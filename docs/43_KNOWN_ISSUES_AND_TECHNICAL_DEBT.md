## Confirmed architectural gaps (not bugs — deliberate stubs/extension points)

4. **Fixed 2026-10-02** — Ed25519 package signing is implemented (`47_PACKAGE_SIGNING.md`); Commerce24's production key still has to be generated and built in (`47` §9). Original entry: **Package signing is architecturally prepared but not cryptographically implemented.** `NullPackageSigner` is the only `PackageSignerInterface` implementation; `verify()` always returns `true`. Package authenticity is NOT currently verifiable beyond content-integrity checksums. (`24_LICENSING_AND_COMMERCE.md`)
5. **`PackageInstallEvent`/`PackageEvent` and `PackageSignedEvent` are unused extension points** — declared but no current code path dispatches them. (`27_EVENTS_AND_HOOKS.md`)

## Confirmed leftover artifacts

6. **`templates/site7-components/clientLogos.twig`** — one leftover file predating the current `_blocks/`-based template architecture. Confirmed dead: no current code path reads or writes it. Harmless but not cleaned up (documentation-only task scope). (`13_TEMPLATE_ARCHITECTURE.md`)

## Confirmed simplifying assumptions

7. **Template install mapping assumes exactly one Matrix block per Section package** — `CraftResourceService`'s own comment describes this as an explicit "MVP: assume first block handle" simplification. (`13_TEMPLATE_ARCHITECTURE.md`)
8. **`CraftSectionImportService` does not dispatch `ResourceImportedEvent` directly** — it relies entirely on the per-Entry-Type delegate (`MatrixEntryTypeImportService`) dispatching it, which happens to produce the same effective backup behavior but is a docblock/behavior mismatch worth noting for anyone reading `CraftSectionImportService`'s own comments expecting a direct dispatch. (`26_BACKUP_AND_RECOVERY.md`)

## Confirmed real-world capture gaps (Website/Starter Kit import path)

9. Per the plugin's own `VALIDATION-REPORT-FULL-PIPELINE.md` (an older document; facts re-verified/summarized here, not depended upon as ground truth per this documentation set's own no-dependency rule): `TemplateGeneratorService::generateFromEntry()` ("Save as Template") only works for pages authored through Site7 Studio's own visual builder — 0 of 885 real traditionally-authored entries qualified in that historical test. ## Absence of certain safety mechanisms (not necessarily bugs, but worth tracking)

10. **RESOLVED (2026-10-05)** — unique DB index on `(packageId, version)` (`17` §7); still no locking, but a racing second insert now fails instead of duplicating. Original: No explicit locking around concurrent version creation for the same package, AND `(packageId, version)` uniqueness is application-level only — there is no DB unique index backing it up. (`17_PACKAGE_VERSIONING.md`)
11. **RESOLVED (2026-10-05)** — install skips a file another package already owns, and refuses targets outside the frontend sources or PHP files; the latter was a real hole (an imported package could create e.g. `web/x.php`) (`21`). Original: No cross-package `targetPath` collision detection for owned files — two different packages could declare ownership of the same target path with no guard. (`21_FRONTEND_FILE_OWNERSHIP.md`)
12. No index for querying `site7_installed_files` baselines across packages by `targetPath` alone (only the composite unique index) — not currently needed by any code path, but would matter if a cross-package ownership audit feature were ever built (see item 11). (`16_INSTALLED_FILE_BASELINE.md`)

## Confirmed architectural gaps found during this documentation-validation pass

15. **RESOLVED (2026-10-05)** — Page sync now has a change gate, goes through `VersionManagerService::createVersion()` and recaptures values like the import (`18` §5a). Rows written before the fix keep their missing `archivePath`. Original entry: **`PageUpdateService` (Page-package Sync From Source) does not conform to the guarantees `SectionUpdateService` provides.** No change-detection gate (writes + creates a version on every call, even when nothing changed), bypasses `VersionManagerService` entirely (no semver bump, no `archivePath` — permanently blocking rollback for these version rows — and a non-standard checksum scheme). Repeated syncing of an unchanged Page produces duplicate `site7_package_versions` rows, since `(packageId, version)` has no DB-level uniqueness (item 10 below) and this path skips the application-level dedup check other writers use. (`18_SYNC_FROM_SOURCE.md` §5a, `17_PACKAGE_VERSIONING.md`)
16. **RESOLVED.** `PackageActionController`'s `install`/`enable`/`disable`/`remove`/`detach` actions now require the `managePackages` permission (the same permission already used by `CommerceController` for its own package install/remove actions), in addition to `requirePostRequest()`. `detach` keeps its pre-existing Dev-Mode gate as an additional layer on top of the permission check. `delete` was intentionally left out of scope for this fix and remains Dev-Mode-gated only. (`28_CONTROLLERS_AND_ROUTES.md` §10, `31_SECURITY_AND_VALIDATION.md`) — **Not yet independently live-verified**: this Craft install is capped at a single user (edition/license limit confirmed live — `ddev craft users/create` fails with "The maximum number of users has already been reached"), so authorized-vs-unauthorized click-through testing could not be performed in this environment. Needs re-verification on a multi-user-capable install before being treated as fully proven in production.
17. **The Starter Kit Build phase (`StarterKitBuilder`) has no CP entry point** — reachable only via `php craft site7-studio/make/starter-kit`. Two other, unrelated CP-reachable "Starter Kit" flows exist (`PackageAuthoringController::actionSaveStarterKit`, `StarterKitGeneratorController`) that don't produce a `blueprint.json` and aren't part of this system. (`32_STARTER_KIT_SYSTEM.md` §14)

## Confirmed bugs found and fixed after this documentation set's creation

18. **RESOLVED (2026-08-18).** Clicking the "Add Section" button injected into a Matrix field could silently trigger Craft's own native single-entry-type "instant add" action in the background, creating an unwanted block independent of the Site7 Content Browser modal (most visible when the field's View Mode is "Blocks" and it allows exactly one Entry Type). Root cause: the injected button shared Craft's generic `btn` class and lived inside the same `.buttons` container Craft's native field JS scopes its own add-button selector to. Fixed by moving the injected buttons to be a DOM sibling of `.buttons` (not a child) and dropping the `btn` class. (`44_CONTENT_BROWSER_MATRIX_INJECTION.md` §11, `39_TROUBLESHOOTING.md` §13)
19. **RESOLVED (2026-08-18, same day as item 18).** Site7's "Add Section"/"Insert Pattern" buttons could be injected into, and a nested field's own native control hidden on, a Matrix-type field nested inside a site7Components block's own entries (e.g. a "CTA Banner" block's own "CTA Button" field). Root cause: `injectButton()` resolved the target field's own `.buttons` container with `.find('.buttons').first()` (an unscoped descendant search that can match a nested field's `.buttons` instead, since Craft renders a field's blocks/entries before its own `.buttons`, sorting the nested one first in DOM order), and the CSS hiding native controls used a descendant combinator instead of a child combinator. Fixed by using `.children()` and child-combinator (`>`) CSS scoping throughout. (`44_CONTENT_BROWSER_MATRIX_INJECTION.md` §11B, `39_TROUBLESHOOTING.md` §14)

20. **RESOLVED (2026-10-02).** Importing an existing block created **duplicate fields** wherever the block's layout renamed a global field (Craft 5 per-layout handles - 47 of rp-craft's 175 block field placements), and lost conditions, non-core field types, nested blocks and UIDs: format v1 (`fields.yaml`/`matrix.yaml`) was a simplified copy. Fixed by Section package format v2 (`schema.json`, `14_IMPORT_EXISTING_SECTION.md` §15). v1 packages still install the old way.
21. **RESOLVED (2026-10-02).** Every package install/enable/disable/remove called `ProjectConfig::rebuild()` (`PackageManagerService::invalidateCraftCaches()`), regenerating the whole project config from the database - which stripped the add-menu groups from every block type of the page-builder Matrix field. Removed; the plugin's changes all go through Craft's services, which keep project config in sync. `ProjectConfigExecutor` (Starter Kit install's "Rebuild Project Config" step, also run by `site7-studio/update` after removals) still rebuilt with the same risk until 2026-10-05; it now saves the buffered changes and writes the YAML (`writeYamlFiles(true)`) instead - verified on rp-craft: `config/project` unchanged, nothing pending, the page-builder's add-menu groups intact. The step is now labelled "Write Project Config".
22. **RESOLVED (2026-10-05).** Several actions changed the site with no permission check, so any logged-in user could call them - Craft checks `accessPlugin-site7-studio` only when a plugin CP *page* is opened, not for action requests (`craft\web\Application`, `!$request->getIsActionRequest()`). Fixed (`31` §4 ACCESS): the Install/Update wizards' steps, `starter-kit-generator/install`, `setup/*` and `settings/test-connection` are admin-only; Shared Resources need plugin access, and Manage Packages to change the registry; `template-generator/save-as-template` needs plugin access and view rights on the entry; Create from Template needs the user's own create-entries permission for the section.
23. **RESOLVED (2026-10-05).** `LogService` could not run on Craft 5 (`Craft::$getLogger()`, and `Site7FileTarget` extended the removed `craft\log\FileTarget`); nothing started it, so the plugin's own log never existed. It now adds a `MonologTarget` from `Site7Studio::init()`'s `onInit` (earlier, Craft rebuilds the targets and drops it): plugin messages also go to `storage/logs/site7-studio-<date>.log`.
24. **RESOLVED (2026-10-05).** The Content Browser put package names, descriptions, categories and handles into its card HTML unescaped - a stored-XSS path for a package imported from an archive. Now escaped, quotes included (`pattern-browser.js` `escapeAttr()`).
25. **RESOLVED (2026-10-05).** `PackageManagerService::getPackagePath()` joined a request-supplied handle into a path unchecked; a handle with `/`, `\` or `..` now resolves to nothing.
26. **RESOLVED (2026-10-05).** Installing a Library Starter Kit on a fresh site (`56` C6, C12, C13) failed or silently did nothing in three ways. (1) If Setup had run first, its empty `site7Components` field conflicted with the Theme's (`ThemeSchemaService::isSetupPlaceholder()` now lets the Theme replace it). (2) Re-running a stopped install failed on plugins it had already installed (`ThemeInstaller` skips them now, as `ThemeUpdater` did). (3) A package row whose folder was gone counted as an import conflict, so the download was skipped while the log said "Downloaded" and the kit installed no pages. `PackageImportService::validatePackage()` now restores the folder, and `KitInstaller::applyKit()` stops if the kit's folder is missing.
27. **RESOLVED (2026-10-05).** The Setup screen asked every new site to pick a page builder. Its Option A created an empty `site7Components` field that no template rendered, and a Starter Kit replaced the choice without saying so. This caused #26 (1) and left a stray "Site7 Components" field on rp-craft. That field had only two test blocks and was shipped to every customer through the Theme; it was removed from rp-craft together with its include in `_layouts/matrix-content.twig`, and the Theme was republished. The Setup screen is removed. The page builder is now Settings → General → Page Builder Field (an existing Matrix field), which a Starter Kit fills in, and the kit's job log names it. `/setup` opens Settings; `make/setup-matrix-field` needs `--field`.
28. **RESOLVED (2026-10-06).** Account & License → Packages → Install answered "Could not install" for any package not in this site's Library: never downloaded, or deleted since. `PackageService::installEntitled()` only installed local packages. It now downloads the package, and whatever it requires that's missing, from Commerce24 first (signature-checked, `LibraryDistribution::closure()` + `download()`). Install → delete → Install again works.
29. **RESOLVED (2026-10-06).** A Starter Kit install stopped at the structure step with "Changes to the project config are not possible while in read-only mode". The Theme copies its `config/general.php` (admin changes only when `CRAFT_ENVIRONMENT=dev`) over the site's before that step, so a site without that variable turned read-only mid-install, after the plugins were installed. `KitInstaller::validateKit()` now refuses when admin changes are off already, and `ThemeInstaller::validateTheme()` when the Theme's `general.php` would turn them off (`CRAFT_ALLOW_ADMIN_CHANGES` overrides, as in Craft) - both before anything changes.
30. **RESOLVED (2026-10-06).** Publish Library with a key that may not publish tried all packages and logged the same 403 for each. `LibraryDistribution::publish()` now stops at the first 401/403.
31. **RESOLVED (2026-10-06).** On a Library site every Section install warned "Shared Resource '…' is not registered": the Theme creates the shared fields but not registry rows. `DependencyResolverService` now accepts a live field of that handle.
32. **RESOLVED (2026-10-06).** The package page's **Remove** button said "This will delete all generated fields, entry types, and templates" but only unlinked the block from the page builder and set the status to available - everything stayed. It now calls `PackageManagerService::uninstallPackage()`: a Section's generated Entry Type, Fields and `_blocks` template are deleted (usage-checked, as Delete), the package stays in the Library and Install rebuilds it. Refused while pages use it. Other package types only change status, and their confirmation says so. `removePackage()` keeps its soft behaviour for Marketplace Reinstall (`12` §5).
33. **RESOLVED (2026-10-06).** An installed Starter Kit or Theme could be disabled or removed: nothing changed on the site, but the Install screen then showed the kit as "Not installed" with a Check that offered to install it again (harmless - existing pages are skipped and edits kept - but misleading), and Updates skipped it. Disable/Remove are now refused for an installed kit or Theme (`PackageActionController::setUpTheSite()`) and hidden on its package page, which says it set up the site; the Install screen counts a disabled kit as installed. It also says, before Check, whether each other kit fits: same Theme → adds its pages; another Theme, or a site with its own structure and no Theme → needs a fresh site (no Check).
34. **RESOLVED (2026-10-06).** Right after the author published, customer sites saw "0 updates available" for up to 5 minutes: `CommerceClient::request()` caches every GET (Settings → Commerce cache duration), the catalog too, and nothing on the Updates screen refreshed it. The Updates list (`LibraryUpdater::availableUpdates()`) and a kit's Check (`LibraryDistribution::check()`) now read the catalog fresh (`catalog(true)` → request option `'fresh' => true`); account and licence reads keep their cache.
35. **RESOLVED (2026-10-06), code review of #28-34.** (1) Remove and Delete now keep a block type that drafts or revisions still use (`removePackageResources()` counts them), and Remove never deletes the source of a block imported from this site (it has an import-source row). (2) The page builder setting can't change while Section packages are enabled in it (they'd stay linked to the old field). (3) A Theme or Library Starter Kit (`PackageManagerService::setsUpTheSite()`) installs only through the Install screen: Install on its package page, Packages → Install and `installEntitled()` refuse it and point there; blueprint kits are unaffected. (4) "Has set up the site" is one rule everywhere (`hasSetUpTheSite()`: enabled or disabled) - Install screen, kit checks, Disable/Remove guard. (5) A package page with no page builder offers Settings only when a Matrix field exists, otherwise the Install screen. (6) The Theme's admin-changes check reads multi-environment config arrays. (7) The kit's early admin-changes check runs only when it's known (env override, or a Theme already installed); otherwise the Theme's own config decides. (8) Packages → Install and `library/download` share `LibraryDistribution::downloadWithRequirements()`, with a fresh catalog. (9) Only the Updates screen, `library/updates` and `update()` read the catalog fresh; Account & License keeps the cache.
36. **RESOLVED (2026-10-06).** Inserting a Template from the Content Browser added its blocks empty - no text, images or block styles - so the section didn't look like the template; a template with no blocks did nothing, silently. Insert now copies the template page's blocks (with content for general pages, layout and styles for detail pages) and isn't offered for a template without blocks (`44` §15). Also: Settings → Commerce named the Account & License page "Commerce & Licensing"; Dev Mode help texts named PHP interfaces; a newly imported block's default description is "The X section.".
37. **RESOLVED (2026-10-06).** A Theme, kit or Theme update installed only on the exact Craft version the Library was built on, so a customer on the next Craft patch was refused. They now install on the same major version (`49` §2a), keeping the site's own Craft in the Composer step; content rows skip columns the site's tables don't have. Not yet verified live: the Composer step on a site whose Craft differs from the Theme's lock (needs a site on another 5.x and internet).
38. **RESOLVED (2026-10-06).** The Theme built its CSS/JS with npm on every customer site, so on hosting without npm (or offline) the site had no styles. It now ships the built frontend (`49` §2b); a fresh install no longer runs npm (6 min instead of ~10).
39. **RESOLVED (2026-10-06).** Account & License showed "Package Usage 92 / 20" - installed packages against the plan's website limit - and nothing enforced a package limit. Plans now carry a package limit for packages beyond the Starter Kit, counted and enforced (`24` §10a). `PlanInfo` also ignores keys Commerce24 adds later instead of failing on them, and the "Storage Usage: Coming soon" placeholder is gone.
