## Confirmed architectural gaps (not bugs — deliberate stubs/extension points)

4. **Fixed 2026-10-02** — Ed25519 package signing is implemented (`47_PACKAGE_SIGNING.md`); Commerce24's production key still has to be generated and built in (`47` §9). Original entry: **Package signing is architecturally prepared but not cryptographically implemented.** `NullPackageSigner` is the only `PackageSignerInterface` implementation; `verify()` always returns `true`. Package authenticity is NOT currently verifiable beyond content-integrity checksums. (`24_LICENSING_AND_COMMERCE.md`)
5. **`PackageInstallEvent`/`PackageEvent` and `PackageSignedEvent` are unused extension points** — declared but no current code path dispatches them. (`27_EVENTS_AND_HOOKS.md`)

## Confirmed leftover artifacts

## Confirmed simplifying assumptions

7. **Template install mapping assumes exactly one Matrix block per Section package** — `CraftResourceService`'s own comment describes this as an explicit "MVP: assume first block handle" simplification. (`13_TEMPLATE_ARCHITECTURE.md`)
8. **`CraftSectionImportService` does not dispatch `ResourceImportedEvent` directly** — it relies entirely on the per-Entry-Type delegate (`MatrixEntryTypeImportService`) dispatching it, which happens to produce the same effective backup behavior but is a docblock/behavior mismatch worth noting for anyone reading `CraftSectionImportService`'s own comments expecting a direct dispatch. (`26_BACKUP_AND_RECOVERY.md`)

## Absence of certain safety mechanisms (not necessarily bugs, but worth tracking)

10. **RESOLVED (2026-10-05)** — unique DB index on `(packageId, version)` (`17` §7); still no locking, but a racing second insert now fails instead of duplicating. Original: No explicit locking around concurrent version creation for the same package, AND `(packageId, version)` uniqueness is application-level only — there is no DB unique index backing it up. (`17_PACKAGE_VERSIONING.md`)
11. **RESOLVED (2026-10-05)** — install skips a file another package already owns, and refuses targets outside the frontend sources or PHP files; the latter was a real hole (an imported package could create e.g. `web/x.php`) (`21`). Original: No cross-package `targetPath` collision detection for owned files — two different packages could declare ownership of the same target path with no guard. (`21_FRONTEND_FILE_OWNERSHIP.md`)
12. No index for querying `site7_installed_files` baselines across packages by `targetPath` alone (only the composite unique index) — not currently needed by any code path, but would matter if a cross-package ownership audit feature were ever built (see item 11). (`16_INSTALLED_FILE_BASELINE.md`)

## Confirmed architectural gaps found during this documentation-validation pass

15. **RESOLVED (2026-10-05)** — Page sync now has a change gate, goes through `VersionManagerService::createVersion()` and recaptures values like the import (`18` §5a). Rows written before the fix keep their missing `archivePath`. Original entry: **`PageUpdateService` (Page-package Sync From Source) does not conform to the guarantees `SectionUpdateService` provides.** No change-detection gate (writes + creates a version on every call, even when nothing changed), bypasses `VersionManagerService` entirely (no semver bump, no `archivePath` — permanently blocking rollback for these version rows — and a non-standard checksum scheme). Repeated syncing of an unchanged Page produces duplicate `site7_package_versions` rows, since `(packageId, version)` has no DB-level uniqueness (item 10 below) and this path skips the application-level dedup check other writers use. (`18_SYNC_FROM_SOURCE.md` §5a, `17_PACKAGE_VERSIONING.md`)
16. **RESOLVED.** `PackageActionController`'s `install`/`enable`/`disable`/`remove`/`detach` actions now require the `managePackages` permission (the same permission already used by `CommerceController` for its own package install/remove actions), in addition to `requirePostRequest()`. `detach` keeps its pre-existing Dev-Mode gate as an additional layer on top of the permission check. `delete` was intentionally left out of scope for this fix and remains Dev-Mode-gated only. (`28_CONTROLLERS_AND_ROUTES.md` §10, `31_SECURITY_AND_VALIDATION.md`) — **Not yet independently live-verified**: this Craft install is capped at a single user (edition/license limit confirmed live — `ddev craft users/create` fails with "The maximum number of users has already been reached"), so authorized-vs-unauthorized click-through testing could not be performed in this environment. Needs re-verification on a multi-user-capable install before being treated as fully proven in production.
17. **The Starter Kit Build phase (`StarterKitBuilder`) has no CP entry point** — reachable only via `php craft site7-studio/make/starter-kit`. Two other, unrelated CP-reachable "Starter Kit" flows exist (`PackageAuthoringController::actionSaveStarterKit`, `StarterKitGeneratorController`) that don't produce a `blueprint.json` and aren't part of this system. (`32_STARTER_KIT_SYSTEM.md` §14)

## Confirmed bugs found and fixed after this documentation set's creation

18. **RESOLVED (2026-08-18).** Clicking the "Add Section" button injected into a Matrix field could silently trigger Craft's own native single-entry-type "instant add" action in the background, creating an unwanted block independent of the Site7 Content Browser modal (most visible when the field's View Mode is "Blocks" and it allows exactly one Entry Type). Root cause: the injected button shared Craft's generic `btn` class and lived inside the same `.buttons` container Craft's native field JS scopes its own add-button selector to. Fixed by moving the injected buttons to be a DOM sibling of `.buttons` (not a child) and dropping the `btn` class. (`44_CONTENT_BROWSER_MATRIX_INJECTION.md` §11, `39_TROUBLESHOOTING.md` §13)
19. **RESOLVED (2026-08-18, same day as item 18).** Site7's "Add Section"/"Insert Pattern" buttons could be injected into, and a nested field's own native control hidden on, a Matrix-type field nested inside a site7Components block's own entries (e.g. a "CTA Banner" block's own "CTA Button" field). Root cause: `injectButton()` resolved the target field's own `.buttons` container with `.find('.buttons').first()` (an unscoped descendant search that can match a nested field's `.buttons` instead, since Craft renders a field's blocks/entries before its own `.buttons`, sorting the nested one first in DOM order), and the CSS hiding native controls used a descendant combinator instead of a child combinator. Fixed by using `.children()` and child-combinator (`>`) CSS scoping throughout. (`44_CONTENT_BROWSER_MATRIX_INJECTION.md` §11B, `39_TROUBLESHOOTING.md` §14)

20. **RESOLVED (2026-10-02).** Importing an existing block created **duplicate fields** wherever the block's layout renamed a global field (Craft 5 per-layout handles - 47 of rp-craft's 175 block field placements), and lost conditions, non-core field types, nested blocks and UIDs: format v1 (`fields.yaml`/`matrix.yaml`) was a simplified copy. Fixed by Section package format v2 (`schema.json`, `14_IMPORT_EXISTING_SECTION.md` §15). v1 packages still install the old way.
21. **RESOLVED (2026-10-02).** Every package install/enable/disable/remove called `ProjectConfig::rebuild()` (`PackageManagerService::invalidateCraftCaches()`), regenerating the whole project config from the database - which stripped the add-menu groups from every block type of the page-builder Matrix field. Removed; the plugin's changes all go through Craft's services, which keep project config in sync. `ProjectConfigExecutor` (Starter Kit install's "Rebuild Project Config" step, also run by `site7-studio/update` after removals) still rebuilt with the same risk until 2026-10-05; it now saves the buffered changes and writes the YAML (`writeYamlFiles(true)`) instead - verified on rp-craft: `config/project` unchanged, nothing pending, the page-builder's add-menu groups intact. The step is now labelled "Write Project Config".
22. **RESOLVED (2026-10-05).** Several actions changed the site with no permission check, so any logged-in user could call them - Craft checks `accessPlugin-site7-studio` only when a plugin CP *page* is opened, not for action requests (`craft\web\Application`, `!$request->getIsActionRequest()`). Fixed (`31` §4 ACCESS): the Install/Update wizards' steps, `starter-kit-generator/install`, `setup/*` and `settings/test-connection` are admin-only; Shared Resources need plugin access, and Manage Packages to change the registry; `template-generator/save-as-template` needs plugin access and view rights on the entry; Create from Template needs the user's own create-entries permission for the section.

58. **RESOLVED (2026-10-15).** Site search found almost nothing on Library sites (site7-qa: 43 index rows for 352 entries): `SiteKitContent::import()` writes rows directly, so Craft never indexed them. Every import now indexes the elements it brought in (`indexForSearch()`, by UID, on each site), and the plugin migration `m261015_120000_reindex_library_content` (schema 1.0.7) queues one `ReindexSearchJob` for sites imported before, which indexes without saving anything.
59. **RESOLVED (2026-10-16).** A Theme install asked the customer to add every variable name in the author's `.env`, including `CRAFT_DB_TABLE_PREFIX` (copying `rp_` would break their site), `C24_SIGNING_SECRET_KEY` and `SITE7_LIBRARY_PATH`. `ThemeInstaller` now reports only names the Theme's own files use (`SiteKitFiles::referencedEnvKeys()`); this also applies to Themes already published.
60. **RESOLVED (2026-10-16).** The unit suite tested the host project's `vendor/site7/studio` copy, not this working tree, once rp-craft installed the plugin from Git: new or changed code wasn't what ran. `tests/bootstrap.php` now loads `site7\studio\` from this `src/` first.
61. **RESOLVED (2026-10-16).** Syncing a block package (Sync From Source, Review & Update, `library/sync-sections`) re-ran `installPackage()`, which set its status to `installed`; enabled blocks dropped out of the Content Browser (it lists `enabled` only) though they stayed in the page builder. rp-craft lost 27 that way on 2026-10-15. Re-installing now keeps an `enabled` or `disabled` status; rp-craft's 27 were enabled again.
62. **OPEN (2026-10-16), mitigated.** Sites on Theme 1.2.1 or older read the Theme's GitHub repositories (`craft5-simple-menu`, `site7-studio`) through GitHub's anonymous API. Once its limit (60/hour) runs out, Composer falls back to an SSH clone and `composer update` fails with "Permission denied (publickey)", so such a site can't update the plugin until the hourly reset. Theme 1.3.0 ships those repositories with `"no-api": true` (HTTPS clone, no limit); `55` §7 lists the workarounds for older sites.
63. **RESOLVED (2026-10-16).** Theme 1.3.0 (built on Craft 5.11.5.1) failed to install on site7-qa (Craft 5.10.8.1): the Theme kept the site's own Craft with `composer require craftcms/cms:5.10.8.1`, and Composer's audit refuses that version (svg-sanitize advisories). The update rolled back cleanly (#52). A site on an older Craft of the same major version now installs the Theme's lock and is upgraded to the Craft the Theme was built and tested on; a newer or other-major Craft is still kept, never downgraded (`ThemeInstaller::keepsSiteCraft()`).
64. **RESOLVED (2026-10-16).** A page renamed on rp-craft comes back under a new Template handle (handles follow the slug) while it is the same entry (`entryUid`). A kit update installed it as a new page: the site's page was kept and the new blocks were added into it, so Blog Pack 1.1.0 left site7-qa's posts with two articles each. `LibraryUpdater::applyKit()` now finds the installed package with that page (`pageOwner()`) and updates the page from it (`applyTemplate()`, the rule: untouched parts replaced, removed blocks trashed, the customer's edits kept); the old package is set back to `available`.
65. **RESOLVED (2026-10-16).** Untouched content counted as "edited here", so updates kept old versions: an entry saved without a change gets an empty value for every field in its layout (`[]`, `false`, `''`), and an earlier update that dropped a field or trashed an element (e.g. the old blog categories) changed the site's rows too. On site7-qa every blog post kept its old title and slug. Empty field values now count as no value (`SiteKitContent::comparableContent()`), and the installed version is compared as this site would hold it now: without values of fields the site no longer has and without references to elements trashed or missing here (`LibraryUpdater::asOnThisSite()`). A customer's real edit still differs and is kept.
