# 32 — Starter Kit System

## 1. Purpose

Document the largest subsystem in the plugin — whole-site capture, build, subprocess-based installation, and synchronization of Starter Kit packages. This is architecturally distinct from (and NOT merged with) the single-file three-way system documented in `19_UPDATE_AND_CONFLICT_HANDLING.md`.

## 2. What It Does

Captures an entire Craft site's structure (or a curated subset) into a portable `blueprint.json`, then installs it onto a target site through a carefully staged, subprocess-isolated executor — because installing a Composer plugin and enabling it via Craft's Plugins service cannot safely happen in the same PHP process.

## 3. Current Status

**Implemented** — build, install (with subprocess orchestration), and whole-site sync are all live. See `15_IMPORT_EXISTING_PAGE_AND_WEBSITE.md` §14 for confirmed real-world capture gaps in the underlying Website import step.

**Not the Library Starter Kit:** a `starter-kit` package with a `starter-kit.json` is a Library Starter Kit (format v2, `51`). It installs through the package manager and the Install screen's own pane. This system's catalog (`StarterKitCatalogService::listAvailable()`) skips it, and this system is otherwise unchanged.

**Important scoping note**: this document covers ONE of three structurally separate "Starter Kit" code paths that exist in the plugin's CP/console surface. The Build→Install→Sync pipeline documented here is the only one that produces a `blueprint.json` and uses `DependencyAnalyzer`/subprocess orchestration — and it is also the only one of the three with **no CP entry point at all**. See §14.

## 4. Architecture

```
BUILD SIDE
  WebsiteImportService (capture, 15_IMPORT_EXISTING_PAGE_AND_WEBSITE.md)
     ↓
  ProjectBuilder — assembles a Project model, adds PlatformConfigService summary
     ↓
  DependencyAnalyzer — computeClosure(): BFS over whole-project CraftResourceRegistry
     graph, narrowed to what THIS manifest needs; produces ordered waves:
     plugins / schema / content / frontend, plus cyclicResources/dependencyRelationships
     ↓
  BlueprintBuilder — Project + InstallationPlan → plain JSON blueprint.json,
     SCHEMA_VERSION = '1', deliberately independent of .s7pkg/manifest.json shape
     ↓
  StarterKitBuilder — top-level orchestrator, writes blueprint.json alongside
     the package's manifest.json (build-only scope: no install/Composer/npm execution)

INSTALL SIDE  (subprocess-per-stage)
  InstallationPlanner — Blueprint → deterministic ordered InstallationPlan (read-only)
     ↓
  InstallationValidator — pure read-only pre-flight checks, dry-run by construction
     ↓
  InstallationExecutor — executes a built plan via per-type StepExecutorInterface:
     ComposerExecutor / ContentInstallExecutor / CraftResourceInstallExecutor /
     FrontendInstallExecutor / NpmExecutor / PluginInstallExecutor / ProjectConfigExecutor
     ↓
  InstallationStageRunner — runs exactly ONE session stage per call, three stages:
     'composer' alone → 'install' (plugin/craft-resource/content/frontend/npm) → 'project-config' alone
     ↓
  InstallationOrchestratorService — spawns `php craft site7-studio/install/run-stage <uid>`
     as a FRESH OS SUBPROCESS for every stage (Symfony\Component\Process\Process,
     STAGE_TIMEOUT_SECONDS = 900)

SYNC SIDE  (whole-site, structurally separate from 19_UPDATE_AND_CONFLICT_HANDLING.md)
  SynchronizationPlanner — diffs previously-installed Blueprint vs a newer one,
     classifies changes, produces SynchronizationSteps shaped like Phase 6's
     InstallationSteps (re-executed via the SAME install machinery — idempotent by design)
     ↓
  SynchronizationValidator — read-only: Craft version, plugin version (Composer\Semver\Semver),
     Project Config drift, npm availability
     ↓
  SynchronizationOrchestratorService — applies a confirmed SynchronizationPlan by re-running
     Phase 7's InstallationSession + InstallationOrchestratorService UNCHANGED against the
     new Blueprint
     ↓
  InstalledStarterKitTrackingService — pure persistence via InstalledStarterKitRecord,
     recordInstall(handle, version, blueprint) — this IS the baseline every sync plan diffs against
```

## 5. Execution Flow

**Build**: `StarterKitBuilder::build()` → `ProjectBuilder` assembles the `Project` → `DependencyAnalyzer::computeClosure()` narrows the whole-project graph → `BlueprintBuilder` serializes to `blueprint.json`.

**Install** (why subprocess-per-stage — verbatim from `InstallationOrchestratorService`'s docblock):
> "Every stage is executed inside its own freshly spawned `php craft site7-studio/install/run-stage <uid>` subprocess instead, which is what actually gives Phase 6's proven finding a real fix: installing a plugin via Composer and then enabling it via Craft's Plugins service cannot happen in the same PHP process (Craft caches its Composer-plugin manifest once per process). A generic Craft queue runner alone doesn't guarantee that separation — `queue/run`/`queue/listen` process many jobs in one long-lived loop within a single process — so this class provides the actual OS-level process boundary explicitly."

Both `InstallStarterKitJob` (queue job) and `InstallController::actionRun` (console) call `runToCompletion()`, which loops spawning `runStageSubprocess()` until `$session->isDone()`. The console entry point for each individual stage is `InstallController::actionRunStage(string $sessionUid)`, which calls `installationStageRunner->runNextStage($session)` — **not meant for direct human invocation** (`30_CONSOLE_COMMANDS.md`).

**Sync**: `SynchronizationPlanner` diffs the installed baseline (`InstalledStarterKitTrackingService`) against a newer Blueprint, producing steps shaped identically to installation steps, so `SynchronizationOrchestratorService` can apply them by re-running the EXACT SAME `InstallationSession + InstallationOrchestratorService` machinery — no separate apply-mechanism was built for sync.

## 8. Filesystem Impact

Varies per step executor: `ComposerExecutor` runs Composer operations, `NpmExecutor` runs npm operations, `CraftResourceInstallExecutor` creates native Craft resources (Fields/Sections/etc., `10_CRAFT_CMS_RESOURCE_ARCHITECTURE` — see `04_CRAFT_CMS_INTEGRATION.md`), `ContentInstallExecutor` creates Entries/content, `FrontendInstallExecutor` writes frontend files, `ProjectConfigExecutor` applies Project Config changes.

## 9. Events

`InstallStarterKitJob`/`SyncStarterKitJob` are Craft queue jobs (progress-reportable); no confirmed custom domain events dispatched by this subsystem specifically (distinct from the events in `27_EVENTS_AND_HOOKS.md`, which are mostly import/publishing/commerce).

## 10. Validation and Safety

**Two independently-discovered Craft per-process state-caching bugs** motivate the subprocess architecture — the Composer/Plugins-service caching issue (quoted §5) is the one directly documented; research did not locate a second explicitly-named bug beyond this, though the summary in prior context referenced "two independently-discovered" bugs — treat this as a single confirmed, well-documented instance unless further code evidence surfaces a second.

**Idempotency**: `SynchronizationPlanner` produces steps shaped identically to installation steps SPECIFICALLY so they can be re-executed via the same, already-idempotent install machinery — sync doesn't need its own idempotency guarantees, it inherits them.

**Read-only validators**: both `InstallationValidator` and `SynchronizationValidator` are pure read-only/dry-run by construction — no mutation happens during validation, only during the subsequent execute step.

## 11. Failure Scenarios

| Scenario | Behavior |
|---|---|
| Subprocess for a stage crashes/times out (>900s) | `InstallationOrchestratorService`'s `STAGE_TIMEOUT_SECONDS` bounds it; session state persists for potential resume |
| Craft version incompatible with the Blueprint's requirements | `SynchronizationValidator` catches this via `Composer\Semver\Semver` version comparison before any apply step |
| Project Config drift detected mid-sync | `SynchronizationValidator` flags it as a read-only pre-check |
| npm unavailable on target environment | `SynchronizationValidator` checks npm availability before proceeding |

## 12. Developer Change Guide

If changing installation stage behavior: modify `InstallationStageRunner`/the relevant `StepExecutorInterface` implementation — never bypass the subprocess boundary by trying to run Composer-then-Plugins-enable in one process, that's the exact bug this architecture fixes.

If changing sync behavior: modify `SynchronizationPlanner`'s diff/classify logic — the apply side (`SynchronizationOrchestratorService`) deliberately reuses install machinery unchanged; don't fork a separate apply path.

## 14. Known Limitations

Inherits the Website-capture gaps documented in `15_IMPORT_EXISTING_PAGE_AND_WEBSITE.md` §14 (Category/Tag values, blank-title entries, etc.) since this system's input is that capture step's output. This is structurally a SEPARATE three-way-comparison system from `PackageUpdatePlanner` (`19_UPDATE_AND_CONFLICT_HANDLING.md`) — deliberately not merged, per `01_ARCHITECTURE.md`.

**The Build phase documented in §4/§5 above has no CP entry point.** `StarterKitBuilder` is reachable only via `php craft site7-studio/make/starter-kit "<name>" --entryIds=...` (`MakeController::actionStarterKit()`, `src/console/controllers/MakeController.php:106`) — its own docblock states it was "already fully implemented but had no controller/console entry point calling it" before this command was added, and no CP wizard or button invokes `StarterKitBuilder` today. The **Install** side, by contrast, is fully CP-wired (`InstallWizardController`) — so Build is CLI-only while Install is CP-only-reachable-content, an asymmetry a CP-only user will not discover.

**Two other, structurally separate "Starter Kit" flows exist in the CP and are easily confused with the system documented here — neither produces a `blueprint.json` and neither uses any class listed in §6:**
1. `PackageAuthoringController::actionSaveStarterKit()` (`src/controllers/PackageAuthoringController.php:348`) → `PackageAuthoringService::saveStarterKitComposition()` — saves a "Starter Kit Builder" canvas composition.
2. `StarterKitGeneratorController::actionSaveAsStarterKit()`/`actionInstall()` (`src/controllers/StarterKitGeneratorController.php:60,108`) → `StarterKitGeneratorService::generateFromEntries()` / `StarterKitInstallationService::installStarterKit()` — an older, simpler "capture Entries → install Entries" flow with no `blueprint.json`, no `DependencyAnalyzer`, no subprocess isolation.

Anyone extending "the Starter Kit system" should first confirm which of these three they actually mean — they share a name but not an implementation.

### 14.1 Changes to flow #2 ("capture Entries → install Entries")

The following three fixes were made to `StarterKitGeneratorController`/`StarterKitGeneratorService`/`StarterKitInstallationService` (flow #2 in the list above) — **none of this touches the Build→Install→Sync `blueprint.json` pipeline documented in §4-§13 of this file.** Filed here anyway per this plugin's "doc per feature" convention, and because it's exactly the kind of change someone skimming this file for "the Starter Kit system" needs to be warned isn't what they think it is.

**1. The "Pages to Include" checklist (`actionGetEntries()`) no longer silently hides pages.** Previously it only returned Entries whose Entry Type's field layout included the configured Site7 Matrix field — a real page built without that field (a plain About Us/Contact/Services page) simply never appeared, with no explanation. It now returns every Entry site-wide (still excluding Single-section entries — see 14.2), each tagged `eligibility: 'site7'|'native'|'none'` using the same has-Site7-blocks-vs-native-content branching `PageImportService::importFromEntry()` already uses. `starter-kit-wizard.js` renders a badge for `native`/`none` so the user knows what they're getting *before* selecting it. Note this is informational only: `generateFromEntries()` still only successfully captures `'site7'` pages (via `TemplateGeneratorService::generateFromEntry()`, which throws on zero Matrix blocks by design) — selecting a `'native'`/`'none'` page will still be skipped, but that skip is now surfaced visibly (see next point) instead of only in `console.warn`. Actually capturing native-only pages into a Starter Kit page slot was judged out of scope for this pass — see "For Future Work" below.

Performance note: classifying "does this Entry Type have any capturable native field" is cached per `entryTypeId` in `actionGetEntries()`, not recomputed per Entry — `PageImportService::captureNativeFields()`'s classification is a pure function of the Entry Type's field layout, not any one Entry's values (a capturable scalar field is captured even when its value is null; only an unset Assets field is ever omitted). On a real site with thousands of Entries, recomputing per-Entry was measured to be prohibitively slow; per-entry-type caching keeps this endpoint sub-second. The accepted trade-off: an Entry Type whose *only* capturable field is an empty Assets field on the first-checked Entry will be under-classified for sibling Entries of the same type that do have an image selected — a checklist-badge inaccuracy only, `generateFromEntries()`'s actual per-page capture is unaffected.

`generateFromEntries()`'s per-page skip reasons (already existed as the `$skipped` return value) are now shown in the modal itself when non-empty (`Site7StarterKitWizard.showResults()`), not only `console.warn` — the modal stays open with a "N page(s) skipped: <reasons>" list instead of auto-closing on a partial success.

**2. `manifest.siteStructure` — automatic capture of Single-section content.** `PackageManifest::$siteStructure` is a new, always-populated array: `StarterKitGeneratorService::captureSiteStructure()` (called unconditionally inside `generateFromEntries()`, never opt-in) loops every `craft\models\Section::TYPE_SINGLE` section, loads its one existing Entry, and captures its native fields via `PageImportService::captureNativeFields()` — the exact same reuse the Background section of the originating task called for. Each entry is `{sectionHandle, entryTypeHandle, title, fields}`. On install, `StarterKitInstallationService::installSiteStructure()` finds the matching Single section on the target site, loads its (already-existing — Craft auto-creates it with the Section) one Entry, and `setFieldValue()`s every field still present on the target's layout, tolerating missing sections/fields the same way `installGlobals()` already does.

**Do not confuse `$siteStructure` with `$globals`.** They are two structurally unrelated capture mechanisms that happen to serve a similar conceptual purpose:
- `$globals` (pre-existing) captures actual Craft `GlobalSet` elements, produced by the separate `WebsiteImportService` capture flow and restored by `StarterKitInstallationService::installGlobals()`.
- `$siteStructure` (new) captures ordinary Sections of type Single — each with exactly one Entry — which is how this project actually implements Header/Footer/General/Theme-style structural content. **This project does not use Craft GlobalSets for that purpose.** A Starter Kit's manifest can legitimately have content in one, both, or neither array, independently; nothing in either capture/install path reads or writes the other's key.

An Assets field captured inside `$siteStructure` (e.g. General's `logo`/`favicon`) uses the same `AssetCaptureHelper` descriptor (`{__site7Type: 'assets', items: [...]}`) as everywhere else in this codebase — `captureSiteStructure()` passes the Starter Kit's own `$packagePath` so the file is actually bundled (`preview/assets/`) rather than only described, and `installSiteStructure()` must resolve that descriptor via `AssetCaptureHelper::isAssetDescriptor()`/`restoreAssetField()` (mirroring `TemplateInsertionService::createEntryFromTemplate()`'s existing pattern) before calling `setFieldValue()` — passing the raw descriptor array straight through fails with a Craft "Array to string conversion" error, which is exactly what live verification caught on the first pass before this was wired in.

**3. "Update Starter Kit" — edit a Starter Kit's page list without creating a duplicate package.** `StarterKitGeneratorService::generateFromEntries()` takes a new optional third parameter, `?string $existingHandle`. `actionSaveAsStarterKit()` reads an optional `handle` POST param and passes it through — omitted, the original create-new behavior is unchanged (mints a handle via `generateUniqueHandle()`); given, the method verifies a starter-kit package already exists at that handle and **reuses that same `$packagePath`**, overwriting `manifest.json`/`README.md`/preview in place rather than creating a new directory. `$siteStructure` is re-captured fresh on every Update too, not just on first generate.

The CP's "Update Starter Kit" button (`package.twig`, next to "Install Starter Kit" on a starter-kit's detail page, dev-mode gated) opens the same `Site7StarterKitWizard` modal pre-filled from the package's current metadata, with `options.handle` set. `actionGetEntries()` accepts an optional `handle` query param in this mode and pre-checks whichever pages the target's current `manifest.pages` already lists, via `resolvePreSelectedEntryIds()` — matched primarily by `sectionHandle + entryTypeHandle + slug` (manifest.pages never stores a live Entry id, per this codebase's "structural identity only" convention), falling back to a title-only match within the same section/type when the slug has since changed. A page that matches neither is simply left unchecked; Update never fails because a previously-captured page can no longer be resolved.

**Orphaned Templates are never auto-deleted.** Unchecking a previously-included page on Update just stops that page's Template handle from appearing in the new manifest's `pages`/`requires.templates` — the Template package itself is left on disk untouched, per this codebase's standing "never delete without explicit user action" convention (`PageImportService`/`TemplateGeneratorService` never delete on their own either). Note this extends further than just unchecked pages: **every Update re-runs the same per-page capture as a fresh "Save as Template" for every currently-selected page**, which mints a *new* Template package handle each time (`TemplateGeneratorService::generateFromEntry()`'s own `generateUniqueHandle()`) rather than updating a prior Update's Template package in place — so a page updated three times ends up with three Template packages on disk (`about-us`, `about-us-2`, `about-us-3`, ...), only the newest referenced by the current manifest. This was confirmed live during verification. See "For Future Work" below.

**14.1.1 Follow-up: the flat checklist was unusable on a real project, replaced with the shared Website Structure tree.** Live browser testing of 14.1's first pass surfaced two real problems the original flat `actionGetEntries()` list didn't anticipate:
1. Broadening the checklist to "every Entry site-wide" (to fix the original hiding bug) meant a real project's checklist rendered hundreds of rows with **no grouping at all** - unusable.
2. This project's dev/test database in particular has **878 canonical Entries with a blank title** (stress-test debris, confirmed via a direct DB query), which rendered as literally blank, unlabeled checkboxes.

The fix: `actionGetEntries()` was rewritten to return `WebsiteTreeService::buildTree()`'s tree shape (`{channels, structures}` - `singles`/`categories`/`globalSets` stripped, since Singles are captured automatically by `captureSiteStructure()` and Categories/Global Sets were never part of a Starter Kit's page list) instead of a flat array, with blank-titled entries filtered out (a targeted filter applied only in this controller - `WebsiteTreeService` itself stays an unfiltered, faithful mirror of Craft's structure for its other consumers, e.g. "Import Existing Website" intentionally still shows everything). `starter-kit-wizard.js` renders this via `Site7WebsiteTree.render(..., {selectionMode: 'grouped-multiple'})` - **the exact same reusable tree component** already used by the Package Editor's read-only Starter Kit view and "Import Existing Website" (`src/resources/js/website-tree.js`, globally available on every CP page via `PatternMatrixBundle`, no new asset-bundle wiring needed). On this project's real data this took the picker from ~4789 ungrouped rows (878 blank) down to 89 entries, grouped by Section, matching what "Website Structure" elsewhere in the plugin already looks like.

This replaced the earlier `eligibility: 'site7'|'native'|'none'` three-way badge with `WebsiteTreeService::describeEntry()`'s existing `hasSite7Content: bool` (a page either has Site7 blocks or it doesn't) - the finer native/none split was dropped rather than extending the shared `WebsiteTreeService` with per-entry-type-cached native-field classification, to avoid growing a component several other features depend on. `website-tree.js` gained one small additive capability: `entry.included` (set by `WebsiteTreeService::markIncluded()`) now pre-checks a row in **editable** (`grouped-multiple`) mode too, not just its pre-existing `readOnly` browse mode - needed so "Update Starter Kit" can pre-select whichever pages the target's manifest already lists. This is a no-op for every existing caller (`resource-import-wizard.js`), which never sets `entry.included` on a non-readOnly tree.

`WebsiteTreeService::resolvePageUidsFromManifest(array $manifestPages): array` is a new public method - the same "structural identity → live Entry" best-effort resolution logic (sectionHandle+entryTypeHandle+slug, falling back to title) both `StarterKitGeneratorController` (Update-mode pre-selection) and `PackageAuthoringController` (the Package Editor's tree, next paragraph) now share, rather than each controller reimplementing it.

**14.1.2 Follow-up: the Package Editor had no "Update Starter Kit" entry point at all.** Before this fix, opening a `StarterKitGeneratorService`-produced Starter Kit's Edit page (`site7-studio/packages/{handle}/edit`) showed the **wrong UI entirely**: since that flow doesn't set `websiteImportStatus.isImported`, `edit.twig`'s `{% elseif package.type == 'starter-kit' %}` chain fell through to the **hand-authored drag/drop Starter Kit Builder canvas** (`PackageAuthoringController::actionSaveStarterKit()`'s flow #1, a structurally unrelated composition-based Starter Kit type) - which has nothing to do with a captured-Entries Starter Kit's actual manifest shape, and offered no Update trigger relevant to it.

Fixed by giving flow #2 kits their own branch: `PackageAuthoringController::actionEdit()` now sets `$isCapturedStarterKit = true` whenever `package.type === 'starter-kit'`, it's NOT the Import-Existing-Website flow, and `manifest.pages` is non-empty (the discriminator - only flow #2 and the website-import flow ever populate `pages`; the drag/drop Builder flow does not). `edit.twig` gained a new `{% elseif package.type == 'starter-kit' and isCapturedStarterKit %}` branch, inserted before the existing drag/drop-builder catch-all, showing the same "Update Starter Kit" button as the Library detail page plus a **read-only** Website Structure tree (`#site7-sk-tree`, marked via `WebsiteTreeService::markIncluded()` + `resolvePageUidsFromManifest()`) - reusing `starter-kit-sync.js`'s existing unconditional `#site7-sk-tree` renderer verbatim, so this needed zero new JS. The pre-existing `websiteLocked` branch (Import Existing Website's read-only/Synchronize UI) and the drag/drop Builder catch-all are both unchanged and still exactly as reachable as before for their respective flows.

**14.1.3 Follow-up: "Home" (and other Singles) couldn't be selected at all.** 14.1.1's tree rewrite stripped `singles` from the picker entirely, on the assumption that a Single section's content is only ever "site structure" (Header/Footer/General-style, always auto-captured by `captureSiteStructure()`). That assumption was wrong: **"Home" is a Single section too**, but it has its own genuine, page-specific Site7 Matrix content - completely different from the native-scalar-field-only capture `captureSiteStructure()` does. Excluding all Singles meant Home's actual page content could never be captured into a Starter Kit at all.

Fixed by putting `singles` back into the tree `actionGetEntries()` returns (still blank-title-filtered like `channels`/`structures`) - `website-tree.js` already renders a "Singles" group heading out of the box, so no JS change was needed for the picker itself. The harder half: **installing** a Single-targeted page can never go through `TemplateInsertionService::createEntryFromTemplate()` (which always creates a brand new Entry) - Craft never allows a second Entry in a Single section. `TemplateInsertionService` gained `updateEntryFromTemplate(string $templateHandle, Entry $entry): Entry`, which applies a Template's captured Matrix content + entryFields onto an *existing, already-loaded* Entry instead of a new one, sharing the same content-application logic via a new private `applyTemplateContent()` helper (extracted from `createEntryFromTemplate()`, behavior unchanged there). `StarterKitInstallationService::installStarterKit()`'s per-page loop now resolves each page's target Section via its `sectionHandle` and branches: `Section::TYPE_SINGLE` → find that Single's one existing Entry and call `updateEntryFromTemplate()`; everything else → the original `createEntryFromTemplate()` path, unchanged.

Note this is intentionally additive/parallel to `captureSiteStructure()`/`installSiteStructure()`, not a replacement: a selected Single still ALSO gets its native fields captured/restored automatically and unconditionally via the site-structure path regardless of whether it's separately selected as a page - both apply the same source values, so this is idempotent, just mildly redundant when a Single is selected. Not worth optimizing away for this pass.

Live verification: confirmed `Entry::setFieldValue($matrixHandle, ['new1' => ['type' => ..., 'fields' => [...]]])` (the shape both `createEntryFromTemplate()` and the new `updateEntryFromTemplate()` use) **does** persist correctly through a real save+reload round-trip on this project's current Craft/plugin version - a scratch Entry created, saved, and reloaded from the DB retained its Matrix block. This directly contradicts this document's own "Known landmines" note (see the calling agent's system prompt / prior session notes) that this exact code path was "confirmed still open" as a silent-drop bug - either it was already fixed by an unrelated change since that note was written, or the failure mode is narrower than a blanket "always silently drops" (the test block used had no scalar-capturable fields of its own, so field-level content within a block wasn't fully exercised by this check). Flagged here rather than silently assumed fixed - a future session hitting a real "Matrix content didn't persist" report on this path should re-verify with a block that actually has populated custom fields before assuming this is a regression.

**14.1.4 Follow-up: Home showed as disabled/"Imported" in the picker even for a brand-new Starter Kit.** `website-tree.js`'s `Tree.prototype.renderEntryNode()` computed `isLocked` from `entry.importStatus` (set by `WebsiteTreeService::describeEntry()` via `PageImportSourceRepository` - i.e. "has this page already been captured as a standalone Page/Section/Website package via the Resource Importer?") **unconditionally**, regardless of the `showImportStatus` option - only the visible "Imported"/"Open Package →" badge text was actually gated by that option. Any page with Resource-Importer history (e.g. Home, if it had previously been run through "Import Existing Page" in an earlier session) was permanently unselectable in the Starter Kit picker even though `starter-kit-wizard.js` never sets `showImportStatus` - a real page's unrelated import history has nothing to do with whether it belongs in a Starter Kit's page list, and being locked/checked/included in one Starter Kit must never prevent it from also being selected for (or removed from) another.

Fixed by gating the lock itself on `options.showImportStatus`, not just its badge text: `var isLocked = this.options.showImportStatus && (entry.importStatus === 'imported' || entry.importStatus === 'update-available');`. `resource-import-wizard.js` (the only other consumer, "Import Existing Page"/"Import Existing Website") always passes `showImportStatus: true` for both of its `Site7WebsiteTree.render()` calls, so its own lock-to-prevent-duplicate-import behavior is completely unaffected by this change - verified by inspection of both call sites. `starter-kit-wizard.js` never sets it, so Starter Kit page selection is now driven purely by `entry.included` (checked/unchecked), never by unrelated import-history locking.

**14.1.5 Follow-up: a page already captured into a package (e.g. via a prior "Import Existing Page" or Starter Kit capture) was re-captured into a brand new, duplicate Template every time, instead of being reused.** This was the root cause behind 14.1.4's disabled/"Imported" row in the first place - `entry.importStatus` (the very thing the picker was locking on) already meant "this Entry has an existing package tracked against it via `PageImportSourceRepository`", but `StarterKitGeneratorService::generateFromEntries()` never checked that - it unconditionally called `TemplateGeneratorService::generateFromEntry()` for every selected page, minting a new Template handle every single time (this is also what the earlier-flagged "repeated Update Starter Kit mints `about-us-2`/`about-us-3`/`about-us-4`" gap actually was, at its root).

Fixed with a read-check-then-record pattern: before generating, `generateFromEntries()` now calls a new private `findExistingTemplateHandle()`, which looks up `PageImportSourceRepository::findBySourceUid($entry->uid)` - if a tracked package already exists for this exact Entry, its handle is reused directly (no `TemplateGeneratorService` call at all) - "assign the existing package, don't import it again," matching the semantics the "Imported" badge already implied. If no tracked source exists, generation proceeds exactly as before, but the freshly-created Template's provenance is now recorded into the same `PageImportSourceRepository` (`sourceUid`, `sourceHandle` = the entry's slug, `sourceHash` via `EntrySourceHasher::computeHash()` - the same repository/hasher pair `PageImportService::recordSource()` already uses for "Import Existing Page", not a new tracking mechanism) - so the *next* capture of that same page, whether another Update of this same Starter Kit, a different Starter Kit entirely, or even a later "Import Existing Page" run, reuses this same package instead of creating another one. The `record()` call is wrapped in a try/catch that only logs a warning on failure - never fails the whole Starter Kit generation over a provenance-tracking write; worst case, that one page mints a fresh Template next time exactly like before this fix.

Live-verified against this project's actual data: `PageImportSourceRepository` already had a tracked row for "Home" (package handle `home`, from an earlier, unrelated session's capture) - `findExistingTemplateHandle()` correctly resolved it, while an untracked page (Awards) correctly returned null and falls through to normal generation.

**14.1.6 Follow-up: a Single whose own Entry has a blank title (but whose Section has a real name) was silently dropped by 14.1.1's blank-title filter.** Confirmed live: "Google Structure Data" (Single section `googleStructureData`) has a blank `title` on its own Entry, even though the Section itself is clearly named - Craft pre-fills a Single's one Entry's title to match its Section when the Single is created, but that's only a default; it can end up blank (edited out, or the Entry created some other way). 14.1.1's filter treated "blank title" as "stress-test junk, drop it" uniformly for every consumer, which was correct for Channel/Structure entries (genuinely untitled test data) but wrong for a Single, where the Section's own name is a perfectly good, meaningful label that's simply stored one level up from where the filter was looking.

Fixed at the source rather than patching the downstream filter: `WebsiteTreeService::describeEntry()` gained an optional `$fallbackTitle` parameter, passed only by `buildTree()`'s Singles loop (as `$section->name`) - when the Entry's own title is blank, the Section's name is used instead; Channels/Structures never pass this, so their entries are completely unaffected. `StarterKitGeneratorController`'s blank-title filter needed no changes - once `describeEntry()` never returns a genuinely blank title for a Single with a named Section, the filter simply has nothing left to (wrongly) drop. Live-verified: raw and filtered Singles counts now both read 14, with "Google Structure Data" (`#9187`) correctly labeled.

**14.1.7 Follow-up (corrects/refines 14.1.4): the Starter Kit picker should show the "Imported" badge, just never lock on it.** 14.1.4's fix (gate `isLocked` on `options.showImportStatus`) was a reasonable first cut, but conflated two independent questions that turned out to need independently-controlled answers: is the "Imported"/"Open Package →" badge *visible* (useful context - a page shown here already has a Template package, and per 14.1.5, selecting it just reuses that package rather than duplicating it) vs. is the row *locked/unselectable* because of it (correct for "Import Existing Page/Website", wrong for the Starter Kit picker - a Starter Kit only ever references an existing Template, it never creates a competing import the way re-running "Import Existing Page" on an already-imported page would). Gating both on the same single option meant either both were off (14.1.4's fix - no badge, no lock, but also no useful "this page already has a package" context) or both were on (would have re-broken selectability).

Split into two independent `Tree` options: `showImportStatus` (badge/link visibility, unchanged meaning) and a new `lockImported` (whether `entry.importStatus === 'imported'`/`'update-available'` disables the row - defaults `false`). `resource-import-wizard.js`'s two `Site7WebsiteTree.render()` calls ("Import Existing Page"/"Import Existing Website") now pass both `showImportStatus: true, lockImported: true` - fully unchanged behavior, verified by inspecting both call sites. `starter-kit-wizard.js` now passes `showImportStatus: true` (so the informational badge/"Open Package" link show) without `lockImported` (so it defaults `false` - the row stays fully selectable regardless of prior import history).

**14.1.8 Follow-up: 14.1.5's reuse-tracking write incorrectly locked a Starter-Kit-generated Template's Name/Author.** `PackageAuthoringService::isLockedImportedPage()` treats ANY row in `PageImportSourceRepository` for a package as "this is a read-only mirror of live content produced by the Resource Importer - Name/Author stay locked" (`updatePackage()` then silently drops those two fields from any save). 14.1.5 started writing a row into that exact table for every freshly-generated Starter Kit Template too (to support cross-capture reuse) - which meant a Template captured purely via "Save Current Site as Starter Kit" (never run through "Import Existing Page" at all) became incorrectly Name-locked, confirmed live while investigating a user report of exactly this symptom.

Fixed by removing the write entirely: `generateFromEntries()` still does the safe, read-only `findExistingTemplateHandle()` lookup (reusing a package if the Entry was genuinely imported elsewhere already - this never writes anything, so it can't cause locking), but no longer calls `PageImportSourceRepository::record()` for its own freshly-generated Templates. Checked the live DB - the only two rows in that table are `page-about-us` and `home`, both from a genuine, unrelated, pre-existing "Import Existing Page" run (dated well before this bug existed) - no real package was ever actually mis-locked by this bug before it was caught and fixed.

**Trade-off reintroduced (was already the pre-14.1.5 behavior, and remains documented "For Future Work" below):** a page captured into a Starter Kit that was never separately imported via "Import Existing Page" mints a fresh Template handle on every capture again, rather than being tracked for reuse across different Starter Kits. Preferred over reopening the incorrect-locking bug - properly solving both at once would need a NEW, dedicated tracking mechanism distinct from `PageImportSourceRepository` (so "was this genuinely Resource-Importer-imported" and "should a future capture reuse this Template" become two independently-answerable questions, only the first of which should ever lock Name/Author) rather than overloading the one table that already has its own, different meaning.

While fixing this, also caught and fixed an unrelated variable-shadowing bug in the same method: the per-entry loop's local reuse-handle variable was named `$existingHandle`, silently shadowing the method's own `$existingHandle` parameter (used to detect "is this an Update") - meaning the later `if ($existingHandle === null) { FileHelper::removeDirectory(...) }` cleanup-on-failure check was reading the LOOP's last-assigned value instead of the actual Update-mode flag. Renamed the parameter to `$existingStarterKitHandle` and the loop-local to `$reusableHandle` to make them impossible to confuse again.

**14.1.9 Follow-up: the Package Editor's read-only Starter Kit view showed the ENTIRE site (89+ rows) with only a couple of checkmarks scattered through it - easy to mistake for a "only one page selected" bug when it wasn't one.** Live-verified this was never a data bug: `WebsiteTreeService::resolvePageUidsFromManifest()`/`markIncluded()` correctly resolved and marked BOTH pages of a real two-page Starter Kit as `included: true` - the underlying data was always right. The actual problem was the display: `#site7-sk-tree` rendered the full site-wide `WebsiteTreeService::buildTree()` output (every Single/Channel/Structure entry on the whole project) with a checkmark next to the few that were actually included - appropriate for the `websiteLocked` (Import Existing Website) branch, where "included" can plausibly cover most of the site, but a poor fit for a captured Starter Kit that typically references only a handful of specific pages out of a much larger site.

Fixed by replacing the full tree with a compact table for the `isCapturedStarterKit` branch specifically - the exact same "Pages" table pattern `library/package.twig`'s Starter Kit Composition section already uses (Title/Section/Template columns, straight from `manifest.pages`), plus a matching "Site Structure" table for `manifest.siteStructure` (Header/Footer/General-style content - always fully included, no checkbox concept needed since it's never opt-in). `PackageAuthoringController::actionEdit()` no longer builds the full site-wide tree for this branch at all (`$starterKitTree` stays reserved for the `websiteLocked` branch only) - both less wasted work per page load and, more importantly, impossible to misread as "only some pages are included" when they all are.

**Follow-up caught in the same pass: `StarterKitGeneratorService::captureSiteStructure()` had the same blank-title bug 14.1.6 already fixed for `WebsiteTreeService::describeEntry()`, but independently, since it never goes through that method.** "Google Structure Data" showed a blank title in the new "Site Structure" table (`manifest.siteStructure[].title: null` on disk, confirmed) for the exact same reason 14.1.6 found: a Single's Entry can have a blank own title even though its Section has a perfectly good name. Fixed with the identical fallback rule, applied independently in `captureSiteStructure()` (falls back to `$section->name` when the Entry's own title is blank). The one existing affected package (`1-pages-0-global-sets`) was patched directly on disk rather than requiring a full "Update Starter Kit" re-capture to pick up the fix; a scan of every other package's `manifest.json` confirmed no others were affected.

**14.1.10 Follow-up (root cause of what looked like 14.1.9 not "sticking"): "Update Starter Kit" corrupted a Starter Kit that was actually created via the separate "Import Existing Website" flow.** After 14.1.9 shipped, a user report ("Website Structure still only shows Home checked, even after adding About Us") looked at first like a caching regression - extensive server-side verification (compiled Twig cache inspected directly, confirmed `cache-control: no-cache, no-store, must-revalidate` on every CP response ruling out HTTP caching, a direct console-rendered dump of the exact same template+context the controller builds) eventually proved the opposite: the SERVER was correctly computing `isCapturedStarterKit = FALSE` for that specific package, because `getWebsiteImportStatus($handle)->isImported` was `TRUE` for it.

Root cause: the package in question (handle `1-pages-0-global-sets` - the literal auto-generated name/handle already gave this away: "1 page(s), 0 Global Set(s)") was NOT created via `StarterKitGeneratorService::generateFromEntries()` at all - it was originally produced by the older, structurally separate "Import Existing Website" flow (`WebsiteImportService`), which tracks its own provenance in `rp_site7_website_import_sources` (`WebsiteImportSourceRepository`), keyed by `packageId` and recording `sourceEntryUids` (in this case, just Home's uid - matching "1 page(s)"). "Update Starter Kit" was built with no awareness that a `type=starter-kit` package could have come from that other flow - clicking it overwrote `manifest.json` with `StarterKitGeneratorService`'s own shape (now 2 pages: About Us + Home) but left the `WebsiteImportSourceRepository` row completely untouched, still saying "only Home was ever captured." `authoring/edit.twig`'s branching (and the `websiteLocked` branch's own read-only tree, which marks inclusion from that SAME stale `sourceEntryUids` list, not from the manifest's current `pages`) then kept routing to and rendering the OLD flow's view using the STALE tracking data - exactly matching "only Home is ticked," with no bug in the actual resolution/marking logic at all (independently re-verified live: both pages resolve and mark correctly when read from the CURRENT manifest - the bug was that the wrong data source was being read).

This is exactly the confusion `docs/32_STARTER_KIT_SYSTEM.md` §14 already warns about ("Anyone extending 'the Starter Kit system' should first confirm which of these three they actually mean — they share a name but not an implementation") - "Update Starter Kit" was the one that made this mistake in practice, by not checking which of the (at least) two `type=starter-kit`-producing flows a given package actually came from before overwriting it.

Fixed at three layers:
1. **Repaired the one affected package**: deleted its stale `rp_site7_website_import_sources` row directly (packageId 59) - its `manifest.json` was already correct (2 pages) from the user's own Update click, so this alone fixes routing/display for it, no re-capture needed.
2. **UI guard**: `LibraryController::actionPackage()` now computes `isWebsiteImportedStarterKit` (via the existing `PackageAuthoringService::getWebsiteImportStatus()`) and `library/package.twig`'s "Update Starter Kit" button is hidden whenever it's true - it was never gated on this before, which is how the corrupting click became possible in the first place. (`authoring/edit.twig`'s own Update button was already correctly excluded via `isCapturedStarterKit`'s existing `elseif` ordering - no change needed there.)
3. **Defense-in-depth at the service layer**: `StarterKitGeneratorService::generateFromEntries()` now checks `WebsiteImportSourceRepository::findByPackageId()` itself before allowing an overwrite, throwing a clear exception if the target package was Website-Imported - so no future UI entry point (or direct API call) can reintroduce this corruption, even if a UI gate is missed again.

**14.1.11 Follow-up: purely structural Singles (Header/Footer/General/etc.) no longer show as selectable "pages" in the picker at all.** Direct user feedback: these are always auto-included via `captureSiteStructure()` regardless of selection, so showing them as checkable rows was pure clutter with no real choice behind it - selecting one either did nothing new (no Site7 content, so `generateFromEntries()` would just skip it, landing in the visible skip summary for no reason) or was outright redundant (its field configuration is already captured unconditionally).

This also settles a related architectural question raised directly: **should Header/Footer be "imported" as Template/page content at all, or is that a codebase (Twig template) concern, not a content-package concern?** The answer, reflected in how this was fixed: a Single's field *configuration* (footer layout, display toggles, logo, phone number, etc.) is legitimate, useful content - that's exactly what `captureSiteStructure()` already captures, unconditionally, for every Single. But the actual *rendering* - the Twig markup deciding how those field values become HTML/CSS - lives in the site's own `templates/` codebase and is intentionally never touched by this plugin's package system at all (no Template/Section package for this project's Header/Footer captures or ships template markup - only field values). So: Header/Footer never need to be "imported" as page-like Template content unless a specific site genuinely gave them their own independent Site7 Matrix body content (rare/unusual for Chrome elements, but not disallowed - if a Single ever does carry real Site7 blocks, e.g. a promotional banner authored as Site7 content on the Header entry, it becomes selectable here exactly like Home already is).

Implementation: `StarterKitGeneratorController::actionGetEntries()` now filters `tree['singles']` to `hasSite7Content === true` OR `included === true` (the `included` exception - set by `markIncluded()` in Update mode - prevents a Single already captured into the target Starter Kit's current `manifest.pages` from silently vanishing from the checklist and being dropped on the next save, even if it has no live Site7 content right now). Live-verified: for a fresh "New Kit" load, only Singles with real Site7 content show (e.g. a test Single named "RP Test" that happens to carry blocks) - Header/Footer/General/Home/etc. (none of which currently have Site7 content on this project) are correctly hidden; for "Update Starter Kit" against the existing kit, "Home" still shows (marked `included`) even without live content, alongside "RP Test".

**14.1.12 Follow-up: "Home" and "Contact" moved out of Site Structure entirely, into the normal Template/page system - explicit user decision, not a bug fix.** Unlike Header/Footer/General/etc. (pure structural chrome - see 14.1.11), Home and Contact are genuinely navigable, page-like content on this project. The user's explicit instruction: stop auto-capturing them via `captureSiteStructure()` at all; handle them exclusively through the same Template/page mechanism as any other selected page.

Implementation, three coordinated changes:
1. **`StarterKitGeneratorService::PAGE_LIKE_SINGLE_SECTIONS = ['home', 'contact']`** (new public constant, deliberately site-specific/hardcoded - nothing about a Single's own data lets this be inferred generically, since structurally Home/Contact and Header/Footer are the same shape, a Single section with one Entry). `captureSiteStructure()` now skips these two section handles entirely - confirmed live: siteStructure dropped from 13 to 11 sections, `home`/`contact` absent.
2. **`generateFromEntries()` gained a native-content fallback.** Previously, a selected page with no Site7 Matrix content always landed in `$skipped` (the documented "Future Work" gap from 14.1.6 era) - now, when `TemplateGeneratorService::generateFromEntry()` throws for lack of Site7 content, it falls through to `PageImportService::importNativeContent()` (made `public` specifically for this - see that method's updated docblock for why it's called directly rather than through `importFromEntry()`: bypasses the "already imported" guard and, critically, never writes into `PageImportSourceRepository`, avoiding the exact Name/Author-locking regression fixed in 14.1.8). This also incidentally resolves that "Future Work" item generally, not just for Home/Contact - any selected page with no Site7 content but capturable native fields is now actually captured, not just visibly skipped.
3. **`StarterKitGeneratorController`'s Singles filter** gained a third inclusion condition alongside `hasSite7Content`/`included` (from 14.1.11): `sectionHandle` is in `PAGE_LIKE_SINGLE_SECTIONS`. Without this, Home/Contact would have no capture path left at all once excluded from Site Structure - they'd be simultaneously hidden from the picker (no live Site7 content) AND no longer auto-captured (excluded per #1 above), silently losing their content entirely. `WebsiteTreeService::describeEntry()` gained a new `sectionHandle` key (additive, harmless for every other consumer) so the controller can identify these specific Singles within the flat, unwrapped `singles` array.

**Companion install-side fix, required for #2 to actually work end-to-end:** `TemplateInsertionService::createEntryFromTemplate()`/`updateEntryFromTemplate()` both unconditionally required `getTemplateBlocks()` to return at least one block, throwing "no content" otherwise - which a native-only Template (zero Matrix blocks by design, all its content is in `entryFields`) always failed. Both now only refuse when blocks AND `manifest.entryFields` are both empty - i.e., truly nothing to apply.

Live-verified end-to-end (isolated test kit, cleaned up after): selecting Home + Contact for a new Starter Kit correctly produced two Template packages (Home reused the pre-existing `home` package via 14.1.5's reuse check; Contact minted a new `contact` package via the native-content fallback, confirmed NOT written into `PageImportSourceRepository`); `siteStructure` correctly excluded both; Install Starter Kit successfully created/updated both pages (`{"created":2,"skipped":[]}`) - confirming the loosened blocks-guard actually works for a real native-only Template.

**Incident during verification, caught and repaired within the same pass:** an overly-broad cleanup script (written for this verification, not part of the shipped fix) deleted the *pre-existing*, real `home` package - not just the test artifacts - because it walked `manifest.requires.templates` without checking whether each referenced Template pre-dated the test. This broke the user's real, active "First Kit" (`1-pages-0-global-sets`) mid-session. Caught immediately via a direct DB check, repaired by regenerating an equivalent `home` package (same handle, same entry, same capture method - `PageImportService::importNativeContent()`) from the still-live Home entry, and confirmed via a final direct check that "First Kit" resolves both its `page-about-us` and `home` Template references correctly again, and both are `enabled`. Documented here rather than silently fixed, per this plugin's standing "never delete without explicit user action" principle being exactly what this incident violated - a lesson for any future cleanup script in this codebase: always diff against pre-existing state before batch-deleting anything discovered via a manifest's own reference list, never assume "referenced by a just-created test kit" implies "safe to delete."

**For Future Work** (deliberately out of scope for this pass):
- Actually capturing `'native'`-eligibility pages into a Starter Kit (today they're only visibly labeled, then skipped if selected) would mean teaching `generateFromEntries()` to fall through to `PageImportService::importNativeContent()`'s path per page, mirroring `PageImportService::importFromEntry()`'s own branching rather than only reusing its classification half. **Resolved by 14.1.12 above** - kept here for historical reference to the original gap.
- 14.1.5's reuse is intentionally "assign whatever already exists, as-is" - it never re-captures a reused Template's content even if the source Entry has changed since that Template was generated (no staleness/"Update Available" check on this path, unlike `PageImportService`'s own `sourceHash`-based update detection). A future pass could compare the current `EntrySourceHasher::computeHash($entry)` against the tracked `sourceHash` and re-run generation into the SAME existing package's handle when they differ, rather than leaving a stale Template silently reused forever.
- A proper fix for 14.1.8's reintroduced trade-off (cross-Starter-Kit Template reuse for pages never separately imported) needs its own dedicated tracking table/repository, deliberately separate from `PageImportSourceRepository` so "genuinely Resource-Importer-imported" (should lock Name/Author) and "previously captured into some Starter Kit" (should NOT lock anything) stay two independently-answerable questions rather than one overloaded signal.
- 14.1.10's guard is one-directional (blocks Update FROM overwriting a Website-Imported kit). A `type=starter-kit` package produced by the THIRD flow (`PackageAuthoringController::actionSaveStarterKit()`'s hand-authored drag/drop composition) was never checked against this same corruption risk because it has no `manifest.pages` at all (`isCapturedStarterKit` already requires non-empty `pages`, so Update's button never shows for it either) - but if that flow's data shape ever changes to include `pages`, this guard would need revisiting.

### 14.2 On a fresh install, no shipped package had a `blueprint.json` (S7V-002)

Confirmed, not a bug in packaging: `packages/first-kit` (bundled with the plugin) was built by flow #2 (`StarterKitGeneratorService::generateFromEntries()`, §14/14.1 above), which - per this file's own §14 - never writes `blueprint.json`. On a genuinely fresh Craft install, `first-kit` is the ONLY package under `packages/` with `type: starter-kit`, so `StarterKitCatalogService::listAvailable()` (§4-§13's Install Wizard catalog, `InstallWizardController`) correctly discovered it and correctly rejected it: "No blueprint.json found - this package was not built by the Starter Kit pipeline and cannot be installed by this wizard." **Fix**: ran the pipeline that already existed but had never been exercised against real captured content end-to-end - `php craft site7-studio/make/starter-kit "Demo Fresh Site" --entryIds=<id>` (`MakeController::actionStarterKit()`) against a minimal real Entry (one Channel Section, one Entry Type with a Title field and one Plain Text field, one Entry with real field content) - producing `packages/demo-fresh-site/{manifest.json,blueprint.json,README.md}` plus its referenced Template package `packages/demo-home-page/`. No blueprint.json was hand-written; no validation logic was bypassed or special-cased for one handle - `StarterKitCatalogService::isInstallable()`/`installabilityNotes()` (extracted as pure, unit-tested static methods from the previously-private `describe()`, no behavior change) evaluate `demo-fresh-site` exactly the same way they evaluate every other package, and it passes because its blueprint's own `validation.valid` is genuinely `true`.

Live-verified end-to-end on a third, independent fresh Craft install (`site7-validation-3`, separate from the two used for S7V-001): Install Wizard step 1 now shows "Demo Fresh Site v1.0.0" with an active **Select** button (First Kit still correctly greyed out with the same rejection note) → Environment Validation passed → Installation Preview showed 3 planned steps (`Apply Section settings for "Demo Pages"`, `Install captured pages and Global Set values`, `Rebuild Project Config`) → Execute Installation queued an `InstallStarterKitJob` (`site7_install_sessions.status` went `queued` → `completed` after running `craft queue/run`) → the target Section was reused and Entries were created from the captured Template. **This does not add a CP entry point for the Build phase** - that gap, documented above this subsection, is unchanged and still real: producing a new installable kit still requires the console command. Fixing S7V-002 only required that *a* genuine, pipeline-built kit exist and be correctly recognized/installable, not that authoring one become CP-driven.

**Newly observed while installing (NOT fixed here - out of this fix's scope, filed as findings for the next validation phase)**:
- The Execute Installation step produced more than one Entry from a single wizard run (repeat/duplicate `demo-home-page`-slugged Entries), some with a blank title - looks like either the queue job or the wizard's own polling re-triggered `InstallStarterKitJob` more than once for the same session, not a one-shot idempotent install.

- Section-creation/content-quality concerns already known from the S7V validation report (duplicate/blank-titled Entries, whether the target Section's settings genuinely got "applied" vs. just reused because it already existed on this test site) are unchanged and still apply.

### 14.3 Full-site test: rp-craft onto a fresh Craft install (2026-10-02)

Question tested: can a Starter Kit rebuild a site like rp-craft on a fresh Craft? **Not today.** Kit built from 10 rp-craft pages (`make/starter-kit`, entries Home, Contact, About Us, Services, Blogs, one service, one blog post, Header, Footer, General) and installed with `install/run` on a separate fresh DDEV project (Craft 5.10.8.1, same as rp-craft). rp-craft was restored from a DB snapshot afterwards.

**Build side** — blueprint captured 8 sections' settings, 1 asset volume, 2 category groups, 1 tag group, 10 pages, 4 navigation entries, 20 required plugins, 20 npm packages; warned that 48 resources are in circular dependencies. Each page package holds only the page's simple field values (titles, toggles, dropdowns, Assets references). Every Matrix field on rp-craft's pages (`heroBannerSlider`, `standardBannerSlider`, `background`, `spacing`, ...) was excluded as "Not Captured", so page body content doesn't travel.

**Install side**, in order of what blocked it:
1. **Private plugins**: the blueprint records Composer package names only, not repositories. `remoteprogrammer/ai-chat`, `htmlsitemap`, `payment-gateway` (path repos in rp-craft) and `simple-rp-menu` (private VCS repo) can't be resolved on a fresh site, and all plugins go through one `composer update`, so one unresolvable package fails the whole kit. With rp-craft's repositories copied onto the test site, all 20 plugins required and installed.
2. **Kit not registered** — `StarterKitInstallationService::installStarterKit()` looked the kit up in the DB only, but on a fresh site it exists only on disk ("Starter Kit package not found"). **Fixed**: it now falls back to `discoverPackages()`, as its Template lookup already did.
3. **No schema is created** — sections, entry types and fields aren't in the kit. `Apply Section settings` skips every section that doesn't exist yet ("Sections arrive via their Template package's own install"), but Template packages captured from native pages carry no fields/entry types either. All 10 pages were skipped with "Entry Type 'home' / 'standardPages' / 'service' / 'blogET' ... is not installed in this project." The fresh site ended with 0 sections, 0 entry types, 1 field.
4. Asset Volume skipped — filesystems aren't captured.

Worked: category/tag groups, the 10 Template packages registered and installed, frontend config copied, `npm install`, project config rebuild.

**What a full-site kit would need**: the site's schema (sections, entry types, fields incl. nested Matrix entry types, field layouts, filesystems/volumes) — rp-craft's `config/project/*.yaml` already describes exactly this and Craft can apply it; full entry content including nested Matrix entries; Twig templates (`templates/_layouts`, `_components`, `_macros`, section templates), `modules/`, and frontend sources; and Composer repository definitions for private plugins. Until then a Starter Kit is suited to adding pages/blocks to a site that already has the same base schema. The Full Site Kit (`48_FULL_SITE_KIT.md`) covers the schema, code and frontend part (Phase 1, 2026-10-02).
